# 1訪問への複数タスク登録 実装計画

## 1. 文書情報

| 項目 | 内容 |
| --- | --- |
| 文書の目的 | 今まで1件として登録していた勤務内容を「タスク」とし、1件の訪問へ複数タスクを登録できるようにするための要件、設計、移行および実装手順を定める |
| 対象アプリ | TkpSalaryCalculator Android版 |
| 作成日 | 2026-08-30 |
| 最終更新日 | 2026-08-30 |
| 状態 | ユーザー確認および文書レビュー指摘を反映した実装計画 |

## 2. 要件の要約

本対応の要件は、次の一文で表す。

> 1件の訪問の中に、今まで1件ずつ登録していた勤務内容を、複数のタスクとして登録できるようにする。

例えば、現在は同じ訪問で「身体1」と「生活3」を行った場合でも、次のように2件登録する必要がある。

```text
登録1件目：身体1  → 件数手当が1回発生
登録2件目：生活3  → 件数手当が1回発生
```

これを次の構造に変更する。

```text
訪問1件
├─ タスク1：身体1  → 今までの身体1の登録と同じ計算
└─ タスク2：生活3  → 今までの生活3の登録と同じ計算

件数手当は訪問全体に1回だけ発生
```

重要なのは、タスク同士を時間的に連結することではない。各タスクは、今までの勤務登録1件と同じ入力項目と計算方法を持つ。今回追加するのは、それらを「同じ訪問に属する複数タスク」として一括登録する仕組みである。

## 3. 用語

| 用語 | 本計画での意味 |
| --- | --- |
| 訪問／勤務記録 | 件数手当を1回数える単位。画面上で保存・編集・削除する親データ |
| タスク | 今まで勤務記録1件として登録していた内容。サービス種類、時間区分、入力方式、勤務時間、開始・終了時刻を持つ |
| 訪問合計 | 訪問内の全タスクの給与と、訪問に対する件数手当を合計した金額 |

コード上では、既存の`WorkRecord`を訪問を表す親として維持し、その中に1件以上の`WorkTask`を持たせる案とする。

## 4. 現行仕様との関係

特に次の現行仕様を変更する必要がある。

- [要件定義書](requirements.md) `FR-COUNT-02`：現在は勤務記録1件と訪問1件が同じである。
- [給与計算仕様書](salary_calculation_specification.md) 3.1、5～9節：現在は1勤務記録にサービスと時間が1組だけ存在する。
- [画面仕様書](screen_specification.md) `SCR-DAY-01`、`SCR-WORK-01`、`SCR-CALC-01`、`SCR-SHIFT-01/02`：現在は1勤務記録につき1つの勤務内容を入力・表示する。
- [データベース仕様書](database_specification.md) `basic_shift`、`work_record`：現在はサービスと時間の列を勤務記録へ直接保存する。
- [テスト仕様書](test_specification.md) `CALC-*`、`WORK-*`、`SHIFT-*`：現在は勤務記録と勤務内容が1対1である。

「複数の訪問を1件にまとめない」という現行制約は維持する。同じ日の別の訪問は、引き続き別々の勤務記録として登録する。

## 5. 確定する機能要件

### 5.1 訪問とタスク

- 1件の訪問には、1件以上のタスクを登録する。
- 1件のタスクは、今までの勤務登録1件と同じ情報を持つ。
  - サービス設定
  - サービス種類
  - 時間区分または任意の勤務時間
  - 入力方式
  - 開始時刻および終了時刻
- 訪問の日付は全タスクで共通とする。
- タスクは追加、編集、並べ替えおよび削除できる。
- 最後の1タスクは削除できず、タスクが0件の訪問は保存できない。
- 同じ種類のタスクを複数登録することも許可する。
- 本対応では訪問内タスク数の製品上限を新設しない。実装上の固定上限が必要と判明した場合は、タスク0で要件、入力時の案内、インポート拒否条件およびテスト境界を正本仕様へ追加してから実装する。
- 訪問の保存、編集、削除および複製は、含まれる全タスクを一括して行う。

### 5.2 各タスクの時間

- 各タスクの入力方式、勤務時間、開始時刻および終了時刻は独立して入力する。
- 身体1の終了時刻から生活3の開始時刻を自動計算するなど、タスク間の時間関係は設けない。
- タスク同士が連続している、重なっていない、または入力順に実施されたとは仮定しない。
- 各タスクについて、現在と同じ入力検証を行う。
  - 勤務時間方式では勤務分数を入力する。
  - 時刻条件付き割増が対象となる場合だけ開始時刻を要求する。
  - 開始・終了時刻方式では両時刻から勤務分数を算出する。
  - 勤務分数は1分以上1,440分以内とする。
- 日付をまたぐタスクの勤務日、設定年月、曜日、祝日および給与期間は、現在と同じく訪問の日付を基準とする。
- 複数タスクの合計時間に対する新しい上限や、タスク間の重複・空き時間の検証は追加しない。

### 5.3 基本給与と割増

- 各タスクは、今まで勤務記録1件へ行っていた給与計算をそのまま行う。
- 基本単価はタスクのサービス種類と時間区分から選択する。
- 時給方式、固定額方式および丸め規則は変更しない。
- 休日、夜間などの割増条件はタスクごとに判定する。
- 割合加算、時間当たり固定額加算および1件固定額加算はタスクごとに計算する。
- 複数タスクの金額を合計するときは追加の丸めを行わない。

つまり、身体1と生活3を同じ訪問へ入れても、それぞれの基本給与と割増は、現在それらを別々に登録した場合と同じ金額になる。

### 5.4 件数手当（件数加算）

- 件数手当だけはタスク単位ではなく訪問単位で計算する。
- 全サービス対象の件数手当は、訪問内のタスク数にかかわらず訪問へ1回だけ適用する。
- 対象サービスが設定された件数手当は、訪問内のいずれかのタスクがそのサービスに該当するとき、訪問へ1回だけ適用する。
- 同じ件数手当の対象になるタスクが複数あっても、その件数手当は1回だけ適用する。
- 異なる件数手当が複数設定され、それぞれ条件を満たす場合は、各件数手当を1回ずつ適用する。これは現在の「複数の件数加算ルールに一致した場合はすべて加算する」という仕様を維持するためである。

通常の全サービス対象の件数手当だけを使用している場合、挙動は単純に次のようになる。

| 訪問内容 | タスク数 | 件数手当150円の適用回数 |
| --- | ---: | ---: |
| 身体1 | 1 | 1回 |
| 身体1、生活3 | 2 | 1回 |
| 身体1、生活3、移動 | 3 | 1回 |

### 5.5 計算式

```text
タスク給与
  = タスクの基本給与
  + タスクに適用される割増の合計

訪問合計
  = 訪問内のタスク給与の合計
  + 訪問に適用される件数手当の合計
```

例：

```text
身体1の基本給与・割増  1,000円
生活3の基本給与・割増    800円
1訪問当たりの件数手当    150円

訪問合計              1,950円
```

従来どおり2件で登録した場合の2,100円ではなく、件数手当が1回だけの1,950円となる。

### 5.6 未計算

- 1件以上のタスクでサービス、時間区分または単価が不足する場合、訪問全体を未計算とする。
- 計算できるタスクだけを合計した推測金額や、件数手当だけの金額は表示しない。
- 画面では、どのタスクの何が不足しているかを表示する。
- 日別、給与期間別および年間の未計算件数は、タスク数ではなく訪問数で数える。

### 5.7 一覧と計算内訳

- 日別一覧とカレンダーの勤務件数は訪問数とする。
- 日別一覧では、1訪問を1行で表示し、「身体1、生活3」のようにタスクを要約する。
- 計算内訳では、訪問の中に各タスクの基本給与と割増を表示し、その後に訪問の件数手当と訪問合計を表示する。
- 給与期間の基本給与・割増小計は全タスクから集計し、件数手当小計は各訪問から集計する。

### 5.8 基本シフトと日単位複製

- 基本シフトにも複数タスクを登録できるようにする。
- 1つの基本シフトを反映すると、その複数タスクを持つ訪問1件を作成する。
- 基本シフトの同日再反映防止は、引き続き`基本シフトID × 勤務日`を単位とする。
- 基本シフトと手入力訪問の類似判定では、タスクID、表示順および入力元プリセットを除外し、サービス、時間区分、入力方式、勤務分数、開始時刻および終了時刻が完全一致するタスクの多重集合を比較する。タスク順だけが異なる場合も類似とし、一部のタスクだけが一致する場合は類似としない。
- 日単位複製では、元の各訪問と、その訪問に含まれる全タスクを複製する。
- 複製後も訪問数と件数手当の適用回数を維持する。

## 6. ドメインモデルと計算設計

### 6.1 モデル案

Domain層には給与計算と不変条件に必要な値だけを置き、反映元や入力補助などの永続化上の由来情報はApplication層のDTOで保持する。これにより、[ADR-0001](adr/0001-ui-framework.md)で定めた「Domainは給与計算規則、Applicationはユースケースとリポジトリ契約を保持する」という依存方向を維持する。

Domainモデルは次の構造とする。

```text
WorkRecord（訪問）
├─ Id
├─ WorkDate
└─ Tasks [1..N]
   └─ WorkTask（今までの登録1件に相当）
      ├─ Id
      ├─ ServiceId
      ├─ TimeCategoryId
      ├─ InputMode
      ├─ WorkMinutes
      ├─ StartTime
      ├─ EndTime
      └─ DisplayOrder
```

- Domainの`WorkRecord`を訪問全体の不変条件と給与計算を表す集約ルートとする。
- Applicationの`WorkRecordDto`はDomainと同じ親子内容に加え、親へ`SourceBasicShiftId`、`SourceWorkRecordId`、子へ`SourceServicePresetId`を保持する。
- リポジトリ契約はApplicationの`WorkRecordDto`を扱い、保存前と読取後にDomainの`WorkRecord`へ変換して不変条件を検証する。
- `WorkTask`だけを単独保存・削除する公開リポジトリ操作は設けない。
- タスクIDはGUIDとし、訪問の再編集時に同じタスクを識別できるようにする。
- 新規入力でもタスクを画面へ追加した時点でタスクIDを採番し、保存前の入力エラーと計算設定不足を同じタスクへ紐付けられるようにする。
- 表示順は訪問内で重複しない0始まりの連番へ正規化する。
- タスク0件、空または重複したタスクID、重複した表示順、各タスクの不正な時間をドメイン不変条件違反とする。

Applicationの基本シフト契約も同様に、`BasicShiftDto`が1件以上の`BasicShiftTaskDto`を持つ構造にする。`BasicShiftTaskId`もGUIDとし、基本シフトの再編集、並べ替えおよび形式3の往復で同じ子を識別できるようにする。

### 6.2 計算結果案

```text
WorkSalaryCalculation
├─ WorkRecordId
├─ Status
├─ TaskCalculations
│  └─ TaskSalaryCalculation
│     ├─ WorkTaskId
│     ├─ Status
│     ├─ AppliedRate
│     ├─ BasePay
│     ├─ Premiums
│     ├─ TaskSubtotal
│     └─ MissingRequirements
├─ CountBonuses        // 訪問に対して計算
├─ Total               // 全タスク + 件数手当
└─ MissingRequirements // WorkTaskId付きの不足理由を全タスクから集約
```

- `Status`は`Calculated`または`Uncalculated`とし、訪問内の全タスクが計算可能な場合だけ訪問を`Calculated`とする。
- `TaskSalaryCalculation.MissingRequirements`は`WorkTaskId`、安定した理由コードおよび任意の関連設定IDを持つ。
- 訪問の`MissingRequirements`はタスクごとの不足理由を`WorkTaskId`付きで平坦化した読取専用結果とし、画面が該当タスクへ移動できるようにする。
- 未計算タスクの`AppliedRate`、`BasePay`および`TaskSubtotal`は`null`とする。計算可能な別タスクの診断用内訳は保持してよいが、訪問が未計算なら`CountBonuses`は空、`Total`は`null`とし、部分金額を訪問合計として表示しない。
- Applicationの入力検証エラーは`Tasks[{WorkTaskId}].ServiceId`のような安定したフィールドパスを持たせ、保存時に最初の不正タスクへフォーカスできるようにする。

計算順序は次のとおりとする。

1. 全タスクについて、現在と同じサービス、時間区分、時間および単価の検証を行う。
2. 各不足理由へ`WorkTaskId`を付ける。1タスクでも計算設定が不足する場合は訪問を`Uncalculated`とするが、計算可能な他タスクの診断用内訳を作るため処理は継続する。
3. 計算可能な各タスクへ現在の基本給与・割増計算を適用する。この段階では件数手当を加えない。
4. 全タスクが計算可能な場合だけ、訪問内のサービス種類を用いて件数手当をルールごとに最大1回計算する。未計算訪問では件数手当を計算しない。
5. 訪問が`Calculated`の場合だけ、全タスクの小計と件数手当をオーバーフロー検出付きの整数加算で合計する。`Uncalculated`の場合は`Total = null`として返す。

## 7. データベース変更と移行

### 7.1 スキーマ案

現行スキーマバージョン5から6への移行を想定する。

| テーブル | 役割と主な列 |
| --- | --- |
| `work_record` | 訪問。`id`, `work_date`, `source_basic_shift_id`, `source_work_record_id`, `save_operation_id`, 作成・更新日時 |
| `work_task` | 訪問内のタスク。`id`, `work_record_id`, `service_id`, `time_category_id`, `input_mode`, `work_minutes`, `start_time_minutes`, `end_time_minutes`, `display_order`, `source_service_preset_id` |
| `basic_shift` | 基本シフトの親。`id`, `weekday`, `display_order`, `is_enabled`, 作成・更新日時 |
| `basic_shift_task` | 基本シフト内のタスク。`id`, `basic_shift_id`, `service_preset_id`, `service_id`, `time_category_id`, `input_mode`, `work_minutes`, `start_time_minutes`, `end_time_minutes`, `display_order` |

主な制約と索引：

- 子テーブルは親削除時に`ON DELETE CASCADE`とする。
- `work_task(work_record_id, display_order)`と`basic_shift_task(basic_shift_id, display_order)`を一意にする。
- サービス、時間区分およびプリセットへの現在の削除規則を子テーブルの外部キーへ移す。
- `work_record(work_date)`索引を維持する。
- 上記の一意索引は親IDを左端列に持つため、親範囲に属する子の取得にも使用する。`work_record_id`または`basic_shift_id`だけの重複索引は追加しない。
- 現行の`ix_work_record_service_date`は親からサービス列を除くと使用できないため削除する。設定変更プレビューは`work_record(work_date)`で対象年月の親を範囲取得し、一意索引で全子をまとめて取得して訪問単位に評価する。
- サービス起点の検索が実測で必要になった場合だけ、`work_task(service_id, work_record_id)`などの候補を`EXPLAIN QUERY PLAN`と約21.9万訪問の性能試験で評価し、使用されることを確認してから追加する。
- 親にタスクが1件以上あることは、保存・インポートのトランザクション内で検証する。

### 7.2 既存DBの移行

移行は単一トランザクションで行う。

1. 新しい親・子テーブルを一時名で作成する。
2. 既存`work_record`の各行から訪問を1行作成する。
3. 既存行のサービス、入力方式、勤務時間および時刻から、表示順0の`work_task`を1行作成する。
4. 既存`basic_shift`も、親1行とタスク1行へ変換する。
5. 件数、ID、参照元ID、勤務時間、時刻および外部キーを検証する。
6. 旧テーブルを新テーブルへ置き換え、索引を作成する。
7. `PRAGMA user_version = 6`を設定してコミットする。

既存データはすべて「タスク1件を持つ訪問」となるため、移行前後で基本給与、割増、件数手当、日別合計、給与期間合計および年間累計は変化しない。

### 7.3 エクスポート・インポート

- エクスポート形式を現行バージョン2から3へ更新する。
- 現行の逐次転送方式を維持し、形式3では`work_record`、`work_task`、`basic_shift`および`basic_shift_task`を、親IDで関連付けた個別のフラットレコードとして出力する。親レコード内へタスク配列を入れない。
- 形式バージョン1と2は引き続き受け入れ、従来の勤務記録1件をタスク1件の訪問へ変換する。
- 形式3では、タスク0件、重複ID、重複表示順、参照切れまたは不正な時間を確認画面表示前に拒否する。
- インポート候補DBへは親を先、子を後の外部キー順で挿入し、全レコード取込後に親ごとの子件数と業務不変条件を検証する。ファイル内の出現順だけには依存しない。
- 現在の逐次入出力を維持し、1転送レコードを処理するための有界メモリだけを使用して、大量の親子データを全件または1訪問分の配列としてメモリへ保持しない。
- 往復後に訪問ID、タスクID、訪問数、タスク数、タスク順、入力内容、由来ID、計算内訳および件数手当の回数が一致することを確認する。

## 8. Applicationと画面の変更方針

### 8.1 Application

- `WorkRecordDto`と`SaveWorkRecordCommand`をタスクのコレクションを持つ契約へ変更し、各タスク用のDTOと保存入力を追加する。この親子契約はSQLite実装より先に確定する。
- 保存前に全タスクを現在と同じ規則で正規化し、設定不足を検証する。
- 保存操作IDは訪問全体へ適用し、再試行で訪問またはタスクが重複しないようにする。
- `IWorkRecordRepository.UpsertAsync`は親と全タスクを同じトランザクションで置換し、`TryInsertAsync`は保存操作IDの一意制約と親子挿入を同じトランザクションで実行する。
- `FindAsync`、`FindBySaveOperationIdAsync`および`StreamRangeAsync`は、常に全タスクを含む完全な訪問を返す。範囲取得では訪問ごとのN+1クエリを避け、対象訪問と全タスクを定数回のクエリで取得する。
- 保存操作IDが既に存在する場合は、親だけでなくタスクID、順序および全入力値を含む親子ペイロード全体を比較し、同じ再試行なら既存結果を返し、異なる内容なら競合として拒否する。
- `DeleteAsync`は親削除と`ON DELETE CASCADE`により全タスクを同じトランザクションで削除する。
- 設定変更の影響件数は、影響タスク数ではなく重複を除いた訪問数とする。
- 日単位複製、基本シフト反映および給与照会を親子構造へ対応させる。

### 8.2 勤務入力画面

`SCR-WORK-01`では、勤務日を1回入力し、その下にタスクを並べる。

```text
勤務日

タスク1
  サービス：身体1
  入力方式・勤務時間・時刻
  [編集] [削除]

タスク2
  サービス：生活3
```

## 10. テスト計画

### 10.1 給与計算

- タスク1件の訪問は、更新前と同じ基本給与、割増、件数手当および合計になる。
- 身体1と生活3を含む訪問は、両タスクの給与を合計し、全サービス対象の件数手当を1回だけ加算する。
- 同じ件数手当の対象タスクが複数あっても1回だけ加算する。
- 異なる件数手当が複数あり、それぞれ条件を満たす場合は各1回加算する。
- 固定額単価、時給、割合割増、時間当たり割増および1件固定割増を各タスクへ現在どおり適用する。
- 各タスクの時刻条件付き割増を、そのタスク自身の開始・終了時刻で判定する。
- 1タスクが単価不足なら訪問全体を未計算1件とし、部分合計を表示しない。
- 未計算結果は訪問とタスクの`Status`が整合し、不足理由から該当する`WorkTaskId`を取得できる。
- 訪問が未計算の場合は件数手当と訪問合計を返さず、計算可能な別タスクの診断用内訳を訪問の確定金額として集計しない。
- 複数タスクと複数ルールの合算で`long`を超える場合は部分結果を返さない。

### 10.2 入力・UI

- 新規訪問では未選択のタスク1件を表示する。
- 各タスクで現在と同じサービス、入力方式、勤務時間および時刻入力を使用できる。
- タスクの追加、編集、並べ替えおよび削除後に訪問全体のプレビューが更新される。
- タスクごとの時間は独立しており、前後のタスク時刻を自動変更しない。
- 最後のタスクは削除できず、サービス未選択のタスクを保存できない。
- 保存連打でも訪問1件と正しいタスク数だけが保存される。
- 同じ保存操作IDと同じ親子ペイロードの再試行は既存訪問を返し、同じ保存操作IDでタスク内容だけが異なる再試行は競合として拒否する。
- 日別一覧、カレンダー、計算内訳およびホームの勤務件数がタスク数ではなく訪問数になる。
- インポート確認では訪問数とタスク数を区別して表示する。
- 最大文字サイズとTalkBackで訪問とタスクを区別できる。

### 10.3 DB・移行・バックアップ

- 新規DBで親子テーブル、制約および索引が作成される。
- スキーマ5の勤務と基本シフトが、タスク1件を持つ親へ移行される。
- 移行前後ですべての既存代表計算が一致する。
- 移行途中の失敗で旧DBを上書きせず、通常利用を開始しない。
- 親だけ、子だけ、タスク0件、重複順または参照切れを保存・インポートできない。
- `FindAsync`、保存操作ID検索、範囲読取、更新、新規挿入および削除の全経路で親子が欠落しない。
- 親ID＋表示順の一意索引が子の親別取得に使われ、重複する親ID単独索引が存在しない。対象年月の訪問と全タスクを取得する実行計画がN+1にならない。
- 形式1・2を取り込むとタスク1件として復元される。
- 形式3は親と子をフラットレコードとして逐次処理し、往復で訪問ID、タスクID、順序、時刻、参照元および計算結果が一致する。

### 10.4 基本シフト・複製

- 複数タスクの基本シフトを反映すると、訪問1件と全タスクが作成される。
- 同じ基本シフトの同日再反映を防止する。
- 反映または複製途中の失敗で親子をすべてロールバックする。
- 日単位複製で訪問数、各訪問のタスク数、順序および入力内容を維持し、親子IDは新規になる。
- 複製後の各訪問へ件数手当を1回適用する。
- 同じタスク内容で順序だけが異なる手入力訪問は類似警告を出し、一部タスクだけが一致する訪問は類似扱いしない。

### 10.5 性能

- 現行基準の約21.9万訪問・各1タスクで既存の2秒以内というP0条件を維持する。
- 全訪問が2タスクの場合も追加で測定する。
- 製品上限を意味しないP1ストレスケースとして、1訪問に100タスクを持つデータで編集、計算、保存および形式3の往復がメモリ不足なく完了することを確認する。
- 給与期間と年間範囲の読取で、訪問ごと・タスクごとのN+1クエリが発生しない。
- `PERF-001`～`PERF-005`および`PERF-008`に相当する保存後再計算、カレンダー、給与期間切替、内訳、月次・年間同時集計をすべて再計測する。
- 大容量エクスポート・インポートで全親子データまたは1訪問分のタスク配列をメモリへ保持しない。

```text
タスク0 正本仕様の更新
  ↓
タスク1 Domainモデル・親子契約・計算
  ↓
タスク2 DB・リポジトリ・移行
  ├─→ タスク3 勤務Application切替 ─┐
  └─→ タスク6 基本シフト対応 ─────┤ 統合・全体ビルド
                                    ├─→ タスク4 バックアップ形式 ─┐
                                    └─→ タスク5 勤務UI ──────────┤
                                                                   ↓
                                                            タスク7 総合回帰・性能
```

- タスク0～3は順番に実施し、タスク1で親子契約を確定してからタスク2のSQLite実装へ進む。
- タスク6はタスク2の後にタスク3と並行実施できる。
- タスク1～3および6は同じ統合ブランチ上の1マージ単位とし、タスク3と6の完了時に全プロジェクトのビルドと契約テストを通す。中間コミットを個別にビルドする場合だけ旧1タスク契約の一時アダプターを使用する。
- タスク4は勤務と基本シフトの親子契約切替後に実施する。
- タスク5はタスク3および6の統合・全体ビルド後に実施する。
- 製品リリースはタスク0～7がすべて完了してから行う。

## 12. 対象外

- 複数の訪問を1勤務記録へまとめる機能
- タスク間の開始・終了時刻を自動接続する機能
- タスク間の重複、空き時間、移動時間、待機時間または休憩時間の検証・計算
- 訪問先氏名、住所、利用者情報など給与計算に不要な個人情報の追加
- 件数手当額を勤務入力時に手動上書きする機能
- 既存の複数勤務を同一訪問だったと推定して自動結合する移行
- サーバー同期または外部サービス連携

## 13. リスクと対策

| リスク | 対策 |
| --- | --- |
| 訪問数とタスク数を混同する | 要件、DTO、画面ラベル、テストで両者を明示的に区別する |
| 親子契約より先にSQLiteやUseCaseを変更して実装が成立しない | タスク1でDomainとApplicationの最終契約を確定し、タスク1～3および6を同じ統合ブランチ上で実施する |
| 既存のタスク計算まで変わる | 現行の勤務計算をタスク計算として移し、タスク1件の全回帰テストを維持する |
| 未計算理由を該当タスクへ表示できない | 計算結果と入力エラーへ`WorkTaskId`を付け、安定したフィールドパスでUIへ渡す |
| 件数手当をタスクごとに加算してしまう | 件数手当計算をタスク計算から分離し、訪問計算の最後にルールごとに1回だけ行う |
| タスク間の時刻を誤って連動する | 時間値を各タスクへ保存し、独立入力のUI・Domainテストを追加する |
| SQLite移行で既存給与が変わる | 旧勤務を必ずタスク1件へ変換し、移行前後の内訳比較をP0にする |
| 親子読取で性能が悪化する | 対象範囲の親と子を一括取得し、N+1検出と2秒基準を回帰テストする |
| 旧バックアップを復元できなくなる | 形式1・2をタスク1件へ変換して受け入れる |
| 親内のタスク配列で大容量バックアップのメモリ使用量が増える | 形式3も親と子を個別のフラットレコードとして逐次入出力する |
| 複数タスクの類似判定が過剰または不足する | タスク順を無視した完全一致の多重集合比較を仕様化し、一部一致を警告対象にしない |
