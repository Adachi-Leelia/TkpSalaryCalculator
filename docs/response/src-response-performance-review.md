# `src/` レスポンス性能レビュー

## 1. 結論

`src/` 全体は、勤務記録を日付範囲で絞るSQL、WAL、ストリーミング形式のデータ移行、画面単位の取消、設定画面の世代管理など、性能を意識した構成になっている。一方、静的レビューで確認できた設計上の問題と、実機計測で優先的に検証すべき性能リスクがある。

最重要なのは、`Microsoft.Data.Sqlite` の `*Async` APIを「DB処理がUIスレッド外で実行される仕組み」として扱っている点である。同プロバイダーの非同期ADO.NETメソッドは同期実行されるため、現在の `await` / `ConfigureAwait(false)` だけでは、画面から開始されたDB処理を確実にUIスレッド外へ移せない。これは [ADR-0001](../adr/0001-ui-framework.md) とテスト仕様 `ARCH-005` の「DB、ファイル入出力および大規模集計がUIスレッドを占有しない」に抵触する可能性が高い。

次に影響が大きいと見込まれるのは、勤務編集を開くたびに行う全勤務履歴集計、計算内訳画面の非仮想化された大量View生成、1件の内訳表示のための給与期間全体の再計算、およびインポート／エクスポートのレコード単位のFlush・SQLコマンド再作成である。後者4件の実際の所要時間とメモリ影響は、代表端末で測定して確定する。

優先順は次のとおりとする。

1. DB・ファイルI/O・大規模集計をUIスレッド外で実行する境界を設け、`ARCH-005`を満たす。
2. 勤務編集の不要な全履歴検索を除去する。
3. 計算内訳を仮想化または段階表示し、1件内訳には専用クエリを用意する。
4. インポート／エクスポートをバッチ化し、処理段階と進捗を表示する。
5. その後に、設定スナップショットの一括読込・キャッシュ、重複集計、接続初期化を計測ベースで改善する。

## 4. 詳細

### RSP-001: SQLiteの「非同期」呼出しがUIスレッドを退避していない

根拠:

- `TkpSalaryCalculator.Infrastructure.csproj:3` は `Microsoft.Data.Sqlite` 10.0.11を使用している。
- `SqliteStorage.cs:208-219` は `OpenAsync`、`ExecuteNonQueryAsync` を使うが、処理を別スレッドへ投入する境界はない。
- `HomePage.xaml.cs:15-18` などの `OnAppearing` からViewModelのロードをUIスレッドで開始する。
- `ViewModelBase.cs:44-72` はそのまま `operation` をawaitする。
- Infrastructure内では `ConfigureAwait(false)` とSQLiteのAsync APIが広く使われているが、これらはスレッドプールへの投入を意味しない。特に同期完了するSQLite操作では、呼出しから継続までがUIスレッドで進み得る。

影響:

- 給与期間集計、カレンダー、勤務保存、設定読込がUIスレッド上で完結し、タップ、スクロール、ActivityIndicatorの描画を止める可能性がある。
- 画面に `IsBusy = true` を設定しても、その直後にUIスレッドを占有すれば、ローディング表示自体が描画されない。
- SQLを高速化して2秒以内に収めても、数百ミリ秒のフレーム停止は体感品質を悪化させる。

改善案:

- Infrastructure境界にUIスレッド外の実行境界を置き、接続の作成からReaderの完了・破棄までをそこで実行する。給与計算とファイルI/Oも同じ方針で切り分ける。
- 最小実装は、`SqliteDatabase` が公開する操作全体をバックグラウンドへ投入する方式である。ただし、既存の `AsyncLocal` によるambient transaction、取消、例外伝播、接続・トランザクションの所有スレッドを壊さないことを統合テストで確認する。接続やトランザクションを作成後に別スレッドへ渡してはならない。
- 単一のDBワーカーキューは有力な選択肢だが、読取り並行性、WAL、長時間インポート、ambient transactionとの整合を設計・計測してから採用する。書込みだけを機械的に直列化することを、このレビューの必須解としない。
- `StreamRangeAsync` は、画面用の最大約620件ならバックグラウンドでリスト化して返す。21.9万件のエクスポートは、Channel等でバックグラウンドproducerから逐次渡すか、転送処理全体をバックグラウンドで完結させる。
- `Task.Yield` や `ConfigureAwait(false)` の追加だけでは、SQLite操作・給与計算・ファイルI/OをUIスレッド外へ実行する保証にはならない。

検証:

- ViewModelをUIスレッドから実行し、SQL実行、給与計算、ファイルI/Oの実行地点がUIスレッドではないことを、テスト可能なフックで確認する。
- Release APKで集計中のUI heartbeat、フレーム時間、ANRを測定する。

### RSP-002: 勤務編集のたびに不要な全履歴検索を行う

根拠:

- `WorkRecordUseCase.cs:43-50` は編集画面を開くたびに設定、全プリセット、入力履歴、既存記録、祝日を順番に取得する。
- `Repositories.cs:315-345` の入力履歴は、全勤務記録の `GROUP BY source_service_preset_id` と `ORDER BY updated_at_utc DESC ... LIMIT 1` を実行する。
- `work_record.updated_at_utc` を先頭にした索引はないため、最新記録検索は基準データで全体走査・ソートになり得る。
- `UsageCount` と `IsMostRecentlyUsed` はApplication DTOには格納されるが、`src/TkpSalaryCalculator.App` から参照されていない。
- 画面仕様は候補を表示順、同順位なら名前順とし、直近利用・利用回数で並べ替えないことを要求している。

改善案:

- 現行UIで使わない `GetInputHistoryAsync` 呼出しとDTO項目を削除する。これが最小で保守性も高い。
- 将来表示する場合だけ、必要な値を個別取得する。最新記録が必要なら `updated_at_utc DESC, work_date DESC, id DESC` の索引を実行計画・書込みコストとともに評価する。
- 利用回数の永続集計は正本を増やすため、現時点では追加しない。必要性と更新コストを計測してから再生成可能なキャッシュとして設計する。
- RSP-001対応後は、独立した設定・プリセット・既存記録の読取りを `Task.WhenAll` で並行化するか、編集画面用read modelを1回のDBセッションで組み立てる。

### RSP-003: 計算内訳が非仮想化Viewを一括生成する

根拠:

- `CalculationDetailPage.xaml:11` は画面全体を `ScrollView` にしている。
- `CalculationDetailPage.xaml:70-130` は日、勤務、割増、件数加算をネストした `BindableLayout` で描画する。
- `CalculationDetailViewModel.cs:133-159` と `162-222` は取得後に全行の表示用オブジェクトと文字列をUI継続上で一括生成する。
- 基準条件では1給与期間に最大約620勤務があり、各勤務が複数のLabel、Grid、Border、子内訳を持つ。`BindableLayout` はリサイクルされないため、画面外のViewも生成される。

影響:

- DBと給与計算が2秒以内でも、ViewModel変換とネイティブView生成で初回表示が停止する可能性がある。
- 大きなオブジェクトツリーによりGC、レイアウト、スクロールが重くなる。

改善案:

- 日・勤務・内訳を表示用のフラットな行モデルへ変換し、`CollectionView` で仮想化する。
- 代替として、最初は期間合計と日別小計だけを表示し、利用者が日を展開したときに勤務内訳を生成する。
- 1画面に全勤務の全ルール文を常時表示せず、勤務行のタップで詳細を開く段階表示も有効である。
- 大量の表示用文字列生成はバックグラウンドで行えるが、MAUIのViewModel更新とView生成はUIスレッドで行う。仮想化なしにスレッドだけ変えても解決しない。

### RSP-004: 1勤務の内訳でも給与期間全体を再計算する

根拠:

- `CalculationDetailViewModel.cs:126-159` は、日・勤務IDが指定された場合も給与期間を解決し、`GetPayrollPeriodAsync` を呼ぶ。
- その後 `selectedDate` と `selectedWorkRecordId` で表示対象を絞るだけである。
- 非表示になる期間全体の `Allowances` と `PremiumTotals` も先に生成する。

改善案:

- `ISalaryQueryUseCase` に `GetWorkRecordCalculationAsync(workRecordId)` または `GetDayAsync(date)` を基にした専用read modelを追加する。
- ID検索、対象月の設定、該当祝日版だけを取得し、1勤務だけ計算する。
- 給与期間全体の内訳と、日／勤務単位の内訳を別ユースケース・別DTOに分ける。これにより過取得が型で見える。

### RSP-005: インポートがレコード単位処理を複数段で繰り返す

根拠:

- `DataTransferUseCase.cs:65-74` は256件ごとにステージへ渡す点はよい。
- しかし `SqliteDataTransfer.cs:279-297` は各レコードをJSON要素へ変換し、SQLコマンドを都度生成してステージDBへINSERTする。
- `SqliteDataTransfer.cs:645-685` はステージDBに保存したJSONを1件ずつ再解析し、候補DBへ新しいINSERTコマンドで書く。
- `SqliteDataTransfer.cs:790-803` は全勤務を再走査してDomain objectを構築する。
- `SqliteDataTransfer.cs:923-937` は候補DBからlive DBへのコピーでも、行ごとにINSERTコマンドを作り直す。

21.9万件では、同じ勤務データに対して、入力JSONの逐次解析、ステージ用JSON化・INSERT、ステージJSONの再解析、候補INSERT、全件検証、live DBへのコピーが重なる。これは隔離検証と安全な全置換のための設計でもあるため、削減前に処理時間、ピークメモリ、失敗時復元を測定して安全性とのトレードオフを確認する必要がある。

改善案:

- 最小改善: テーブルごとに `SqliteCommand` を1回prepareし、パラメータ値だけを更新してバッチ内で再利用する。
- 次の改善候補: 汎用JSONステージと候補DBを二重に持たず、ストリーム検証しながら型付き候補DBへ直接投入する。この案は順序・型・重複・参照整合性を「確認前に既存DBを変更しない」まま検証できることを設計・統合テストで示せる場合だけ採用する。
- live置換は、候補DBを `ATTACH DATABASE` できる条件なら `INSERT ... SELECT ...` をテーブル単位で実行し、C#の行単位コピーを避けられる可能性がある。Android、WAL、復元処理、およびアタッチ先パスの安全性を統合テストで確認する。
- `PRAGMA foreign_key_check` と業務検証は維持する。性能改善のために安全な全置換手順を弱めない。

### RSP-006: エクスポートが1レコードごとにFlushする

根拠:

- `JsonDataTransferStreams.cs:34-50` は全レコードの末尾で `Utf8JsonWriter.FlushAsync` を呼ぶ。
- 基準データでは勤務だけで約21.9万回のFlushとなり、AndroidのContentResolver streamへの細かいI/O待ちを大量に発生させる。
- `SqliteDataTransfer.cs:58-65` は各行でDictionaryとJsonElementも作る。
- `JsonDataTransferStreams.cs:57-63` は各レコードでreflectionにより `Value` を取得する。

改善案:

- まずは64 KiB程度または256件ごとのFlushを比較計測し、最終Flushを必ず行う。どちらの場合もライター内部バッファを除き、全レコードを保持しないストリーミング要件は維持できる。
- `DataTransferRecord` に非ジェネリックな値アクセサを持たせ、毎回のreflectionを除く。
- テーブルごとのwriter delegateで `SqliteDataReader` から `Utf8JsonWriter` へ直接書けば、DictionaryとJsonElementの二重表現も除去できる。
- バッチサイズは端末・保存先ごとに計測して決める。

### RSP-007: 長時間処理の待たされ方が一様である

根拠:

- `DataManagementPage.xaml:30` はエクスポート、読込、検証、置換のすべてを「データを処理しています。」という同じローディング表示にする。
- `DataManagementViewModels.cs:78-151` は進捗情報を受け取らず、処理中に明示的に取消すUIを提供していない。画面離脱時の `CancelPendingOperations` による取消とは別の課題である。

改善案:

- `IDataTransferUseCase` へ進捗通知を追加し、少なくとも「読込中」「検証中」「置換中」「画面更新中」を表示する。
- 件数が分かる段階では処理済み件数を表示する。総件数が未確定なら不正確なパーセントは出さない。
- エクスポートと確認前のインポート準備には、処理中に明示的に取消できるUIを設ける。
- live DBの原子的置換開始後は取消不可とし、「安全に置換しています。アプリを終了しないでください」と状態を明確にする。
- 現在の画面内容は可能な限り残し、全画面をスピナーで隠す時間を短くする。

### RSP-008: ホームが明細全体を保持し、内訳画面で再取得する

根拠:

- `HomeViewModel.cs:341-354` は `GetPayrollPeriodAsync` で全日・全勤務の内訳を含む `PayrollPeriodSummaryDto` を取得する。
- ホームが使うのは期間、小計、未計算数、勤務有無が中心だが、`Summary` は勤務ごとの割増・件数加算まで保持する。
- `HomeViewModel.cs:392-394` は内訳画面へ期間キーだけを渡し、`CalculationDetailViewModel.cs:133` で同じ期間を再取得・再計算する。

改善案:

- ホーム用の軽量 `PayrollPeriodOverviewDto` と、内訳用DTOを分ける。
- または、期間キーとデータ世代をキーにした短命Sessionキャッシュへ計算結果を置き、内訳画面で再利用する。
- キャッシュは勤務、設定、締め日、月額手当の世代変更とインポート成功時に破棄する。正本にはしない。
- 先にRSP-001〜RSP-004を直し、再取得とキャッシュのどちらが単純かを計測して決める。

### RSP-009: 最新の期間切替が古い処理の完了待ちになる

根拠:

- `HomeViewModel.cs:316-339` は要求をキューに直列化する。
- 中間要求はスキップするが、最新要求も実行中の古い要求が終わるまで開始しない。

改善案:

- latest-wins方式にし、新しい期間要求で古い読取・計算のCancellationTokenを取消す。
- 前の結果は新しい結果が確定するまで表示し、期間ヘッダー付近だけに更新中状態を出す。
- RSP-001のDB実行境界で取消チェックを設け、Readerループと日別計算の間でも応答できるようにする。

### RSP-010: 不変スナップショットを多数のSQLで繰り返し組み立てる

根拠:

- `SettingSnapshotRepository.cs:222-253` は1スナップショットにつきheader、services、categories、rates、premiums、bonusesを順番に取得する。
- Premiumの子条件とBonusの対象サービスの読取りを含めると、1スナップショット当たり複数のSQLが発行される。
- `SettingSnapshotRepository.cs:40-69` は要求月ごとに有効IDを検索し、異なるIDを順番にロードする。
- スナップショットと祝日版は不変であり、読取り再利用に向く。

改善案:

- 月からスナップショットIDへの解決を集合クエリ化し、必要IDの子表を `IN (...)` で一括取得する案を、まず実行計画と実測で比較する。
- または、スナップショットID・祝日版IDをキーにしたサイズ上限付きの不変オブジェクトキャッシュをInfrastructureまたはApplication read model層に置く。
- `setting_month` の参照差替え時は月→IDだけを更新し、不変IDキャッシュは再利用できる。インポート成功時は全破棄する。
- キャッシュ導入はDB仕様どおり、RSP-001対応後の計測で有効性を確認してから行う。

### RSP-011: 接続ごとにPRAGMA設定とWAL確認を実行する

根拠:

- `SqliteStorage.cs:208-219` は接続を開くたびに `foreign_keys = ON`、`journal_mode = WAL`、`synchronous = FULL` を実行する。
- リポジトリ呼出しごとに接続を借りるため、複合画面ロードで同じ設定SQLが繰り返される。

改善案:

- `foreign_keys` と `synchronous` は接続単位設定として維持する。
- 永続する `journal_mode = WAL` はDB初期化・マイグレーション時に一度確認し、通常の接続Open経路から外す。
- 変更前後で新規DB、既存DB、インポート候補DB、再オープン時のPRAGMA値を統合テストする。

### RSP-012: 給与期間内で小さな重複計算を積み上げる

根拠:

- `SalaryQueryUseCase.cs:171-180` は同じ設定月の日ごとにサービス名・時間区分名のDictionaryを作り直す。
- `SalaryQueryUseCase.cs:133-140` で日別集計を作った後、`SalaryCalculator.cs:444-476` の期間集計検証が各日を `new SalaryCalculator().AggregateDay` で再集計する。

改善案:

- 表示名Dictionaryを `SalaryCalculationContext` にスナップショット単位で保持する。
- Applicationが自ら生成した検証済み日別結果については、期間集計で合計だけを1パスで作る内部APIを用意する。
- 公開Domain APIの防御的検証は維持し、境界外から渡される値には従来どおり完全検証を行う。

これは最大約620勤務ではRSP-001〜RSP-006より影響が小さい。可読性を落としてまで先行最適化しない。

### RSP-013: 性能テストが受入時間を判定していない

既存テストはストリーミングと整合性をよく確認しているが、性能受入の自動判定としては不足する。

- `InfrastructureDataTransferTests.cs:109-156` は21.9万件の往復を行うが、時間条件は `Elapsed > 0` だけで、`PERF-006` / `PERF-007` の応答性・所要時間・メモリを判定しない。
- `PERF-001`〜`PERF-005` に対応する、21.9万件DBでの保存・カレンダー・期間切替・集計の計測コードは見当たらない。年間給与見込み累計については、その後`PERF-008`として21.9万件DB、範囲索引利用、ウォームアップ後3回の2秒未満を確認するホスト側回帰テストを追加したが、代表実機のRelease計測は引き続き必要である。
- ViewModel単体テストは非同期順序を確認するが、DB処理中のUIスレッド占有や大量XAML要素の描画時間は検出できない。

改善案:

- PC統合テストでは回帰検知用の緩いベンチマークを別ジョブに置き、SQL実行計画、割当量、相対劣化を記録する。
- 合否判定は仕様どおりRelease APK・代表実機・デバッガーなしで行う。
- `PERF-001`〜`005` は操作開始から結果描画完了まで、`PERF-006` / `007` はUI応答性、ピークメモリ、取消・失敗時の安全性を記録する。UI heartbeatは有用な計測方法の一例であり、代表端末で再現可能な方法を採用する。
- 1回の平均だけでなく、ウォームアップ後の複数回の最悪値を保存する。

追跡状況（2026-09-05）:

- `PERF-001`～`PERF-005`、`PERF-008`および`PERF-010`について、約21.9万訪問の1タスク版・2タスク版を使うホスト統合回帰を追加した。
- `PERF-009`について、1訪問100タスクの編集、計算、保存および形式3往復を自動化した。
- Release APKの描画完了、UI応答性、ピークメモリおよびTalkBackを含む代表端末試験は、引き続きリリース判定時に必要である。

## 5. 良好だった点

次は維持すべきである。

- `work_record(work_date)` 索引と範囲SQLにより、カレンダー・給与期間の通常表示は21.9万件全体ではなく対象期間だけを読む。
- `GetEffectiveForMonthsAsync` と `GetManyAsync` により、勤務1件ごとの設定・祝日N+1検索を避けている。
- 金額・時間は整数で、給与計算量は概ね「対象勤務数 × ルール数」で予測可能である。
- 設定スナップショットと祝日版が不変なので、安全な読取りキャッシュを追加しやすい。
- インポートは全件を1つのオブジェクトグラフとして保持せず、256件バッチでステージする。
- WAL読取スナップショット、トランザクション、置換後検証、失敗時復元を重視しており、性能改善時もこの安全性を維持できる構造である。
- `ViewModelBase` の世代管理は、画面へ戻るたびの無条件再読込を抑えている。
- `CalendarViewModel` は月初回ロードで選択日も同時に返し、初回表示時の月＋日二重検索を避けている。

## 7. 推奨する実装単位

### 第1段階: UI停止をなくす

- DB・ファイルI/O・大規模集計をUIスレッド外で実行する境界を導入する。
- 画面用DB読取、給与計算およびファイルI/OがUIスレッド外であることを自動確認する。
- `PERF-001`〜`005` の計測点を入れる。

完了条件: DB・給与計算・ファイルI/O中もUI応答性を維持し、代表実機のP0ケースが2秒以内。

### 第2段階: 日常操作の無駄をなくす

- 未使用の入力履歴検索を削除する。
- 1勤務内訳の専用クエリを追加する。
- 計算内訳を仮想化または日単位の遅延展開にする。
- 期間切替をlatest-winsにする。

完了条件: 21.9万件DBでも勤務編集のオープン時間が全保持件数に比例せず、計算内訳の初期View数が表示範囲に近い。

### 第3段階: 大容量データ移行をバッチ化する

- JSON Flushをバッチ単位にする。
- SQLite commandをprepare・再利用する。
- 候補DBからlive DBへの集合コピーを検討する。
- 段階、件数、取消可能性を画面に表示する。

完了条件: `PERF-006` / `007` でUIが無応答にならず、ピークメモリが端末上限内で、失敗時に既存DBが維持される。

### 第4段階: 小さな重複を計測して整理する

- スナップショット一括取得または不変キャッシュを評価する。
- 接続PRAGMAを整理する。
- 日別辞書・再集計を共通化する。

完了条件: 実装複雑度を増やさず、計測上の改善が確認できること。

## 8. 計測時に残す記録

各ケースで次を残す。

- APK構成、アプリ版、DBスキーマ版、同梱祝日版
- 端末機種、Android版、空き容量、電源・温度状態
- データ件数、対象期間件数、設定・割増・件数加算ルール数
- 操作開始、最初の視覚フィードバック、データ準備完了、描画完了の各時刻
- UI応答性（可能ならUIスレッドの最長停止とフレーム時間）、GC回数、割当量、ピークメモリ
- SQLごとの回数・時間と `EXPLAIN QUERY PLAN`
- ウォームアップ回数、試行回数、最悪値

特に「2秒以内」だけでなく、操作直後にローディング状態が描画されるか、古い要求を待たされないか、取消可能な処理を取り消せるかを記録する。
