# 応答性改善ガイド

## 1. 目的

利用者から「動作が遅い」と報告された場合に、推測で最適化せず、実測結果を基に原因を特定して改善するための手順を定める。

性能改善によって、給与計算の正しさ、設定履歴の再現性、データ整合性、オフライン動作、既存のアーキテクチャを損なってはならない。

## 2. 調査手順

### 1. 遅さを再現する

まず利用者が遅いと感じる代表的な操作を確認する。

例:

* アプリ起動
* 画面遷移
* カレンダー表示・月移動
* 日付選択
* 勤務入力
* 保存
* 設定画面の表示・保存

「全体的に遅い」という報告であっても、最初からすべての操作を詳細計測する必要はない。代表操作を確認し、遅延の傾向を把握する。

### 2. ベースラインを測定する

変更前の応答時間を記録する。

可能な限りRelease APKと実機を使用する。

実機を現在の環境から計測できない場合は、Debug、エミュレーター、PC上の結果を正式な性能判定として扱わない。必要な計測コードまたは手順を用意し、実機での確認が必要であることを明示する。

### 3. 遅い処理を分解する

遅延を確認した操作について、必要に応じて以下の区間へ分けて計測する。

* UIイベント・画面遷移
* ViewModel
* Application / UseCase
* SQLite・ファイルI/O
* Domain計算
* UI状態更新・描画

推測だけでキャッシュ、並列化、SQL変更などを行わない。

### 4. ボトルネックを特定する

計測結果から、利用者の待ち時間に最も影響している処理を優先する。

特に以下を確認する。

* UIスレッド上の重い処理や同期I/O
* 不要または重複したデータ取得
* N+1問い合わせや不適切な取得範囲
* 不要な再計算
* 二重ロード
* 過剰な`PropertyChanged`
* コレクションの逐次更新
* 画面表示ごとの不要な再取得・再生成

コード上で非効率に見えるだけの処理を、実測根拠なしに性能問題と判断しない。

### 5. 最小限の改善を行う

確認されたボトルネックに対して、影響範囲が最も小さい変更を優先する。

キャッシュを導入する場合は、次を明確にする。

* 何をキャッシュするか
* いつ無効化するか
* 元データから再構築できるか
* 正しさをどのテストで保証するか

性能のために必要な表示データや計算入力を省略してはならない。

### 6. 再計測する

変更後は、変更前と同じ操作を再計測する。

少なくとも以下を確認する。

* 変更前の時間
* 変更後の時間
* 改善量
* 関連する既存テストが成功すること
* 他の主要操作に明らかな性能悪化がないこと

改善が不十分な場合は、次に大きいボトルネックについて同じ手順を繰り返す。

## 3. 完了条件

性能改善は、次を満たした時点で完了とする。

* 遅延の原因が実測結果によって説明できる
* 対応した変更と原因が対応している
* 変更前後の結果を比較できる
* 機能上の正しさを維持している
* 未解決の性能問題がある場合は明示している

具体的な性能目標値や回帰試験を正式な受入基準とする場合は、実測結果を踏まえて`requirements.md`および`test_specification.md`で別途定義する。
